# 界面与交付附加条款（可选）

作者：项目所有者提供的附加政策，适用于以界面质感为核心的项目（前端、小程序、App、H5）。
生成 AGENTS.md 时，若目标项目属于此类，或用户要求固化界面与交付规范，把这些条款**原样**写进目标文件，
放在基线「工作原则」之后、单独一节（建议标题：`界面与交付（本项目附加）`），保留用户措辞，不改写成通用准则。

与基线的关系：本节是**追加**政策，不替换基线条款。与基线冲突时（例如本项目要求每轮大规模改动必须做独立评审），
以本节为准，并在目标文件里保留基线的其余条款。

## 一、工作原则

1. 前端质感与丝滑动效是核心要求。涉及前端的改动，以高效截图打磨验收为准，避免反复连续截图。
2. 代码开发不重复造轮子，优先参考对应成熟项目的源代码。
3. 拒绝过度开发，以优雅为原则，以用户体验为第一性原理。

## 二、界面设计原则

避免不必要的次要标签、说明文字、辅助文案、描述性文字及冗余微文案，依靠布局、视觉层级、间距和清晰的主操作实现界面自解释。

## 三、具体开发要求

1. 优先使用强视觉层级和自解释结构，替代文字说明。默认不添加标语文字、教学段落，不在各区块增设冗余帮助说明；确需补充信息时，优先使用信息图标+悬浮提示（tooltip），不展示常驻次要文字。
2. 保留必要的表单标签和可访问名称，保证界面清爽的同时，不牺牲可访问性。
3. 删除、支付、永久提交变更等危险、不可逆操作，必须配置清晰的后果提示。
4. 删减冗余文字后，需保证新手用户可自主识别操作入口、预知操作结果。
5. 迭代重构现有界面时，优先剔除冗余标签和说明文案，若界面清晰度下降，再优化布局结构与按钮文案。

## 四、交付收尾规范

1. 完成全部开发后，对照本项目全部验收点逐项核对，确认功能、界面、边界情况均满足要求。
2. 整理完整交付物清单，输出部署/使用简要说明。
3. 会话即将结束、项目阶段性完成时，整理本次踩过的坑点，区分两类坑点：
   - A）本项目独有的坑（业务特殊、偶然环境问题、项目定制逻辑）：追加写入当前项目 `AGENTS.md` 的【本项目私有 Gotchas（仅本项目生效）】章节；仅本项目生效，不扩散至其他项目。
   - B）跨项目可复用的 Agent 执行高频坑（通用流程、输出格式、验收逻辑类，多个不同项目都容易复现）：同步更新本文件下方【通用高频 Gotchas（新项目自动继承）】；新增通用坑必须确认具备跨项目参考价值，**业务特有、单次偶然问题禁止写入通用区**。
4. 坑点统一书写格式：
   - 【现象】：错误行为/输出
   - 【触发条件】：什么场景会触发该问题
   - 【规避做法】：明确可执行约束，禁止模糊描述

## 通用高频 Gotchas（新项目自动继承，跨项目复用）

> 此处存放 Agent 执行层面高频通用陷阱，每次生成新项目 `AGENTS.md` 会自动带入；业务特有坑不要写在此处。

- 【现象】：前端验收无限循环多轮截图，反复输出高度相似截图进行打磨
  - 【触发条件】：前端界面改动、界面验收打磨环节
  - 【规避做法】：执行高效截图打磨验收，避免无意义连续重复截图

## 落地提示（不要写进目标文件，仅供生成时核对）

- 第四条涉及 `AGENTS.md` 里的两个 Gotchas 章节：通用区必须从本文件同名的「通用高频 Gotchas」章节原样导入；「本项目私有 Gotchas」只生成空标题与说明，初始无任何条目，禁止从其他项目迁移内容。
- 第三条第 1 点提到的 tooltip：目标平台若不支持悬浮提示（如小程序无 hover 浮层），落地时改用「点按图标弹出说明」的等效形式，并在项目文档里记一句该平台的替代做法。
